# Adrobot

Веб-приложение для создания кампаний Keitaro и управления офферами в потоках. Изменения сначала сохраняются в локальной базе: их можно проверить, отменить или опубликовать в Keitaro.

Стек: **FastAPI, SQLAlchemy 2, Alembic, HTTPX, HTML/CSS/JavaScript**. Для запуска не нужны Node.js и сборка фронтенда. Зависимости зафиксированы в `uv.lock`; для Docker есть экспорт `requirements.txt` с хешами.

## Быстрый запуск

Нужны Python 3.12+ и [uv](https://docs.astral.sh/uv/getting-started/installation/).

```bash
git clone https://github.com/fedor11235/adrobot-keitaro.git
cd adrobot-keitaro
cp .env.example .env
uv sync --frozen
uv run alembic upgrade head
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Откройте <http://127.0.0.1:8000>. Интерактивная документация API: <http://127.0.0.1:8000/docs>.

По умолчанию работает **деморежим**. Он реализует тот же интерфейс интеграции и сохраняет состояние отдельного имитатора Keitaro в `data/keitaro-demo.db`. Перезапуск не сбрасывает локальные черновики или внешний демотрекер. Реальные рекламные кампании в этом режиме не затрагиваются.

## Подключение к Keitaro

В `.env` задайте:

```dotenv
APP_MODE=live
DATABASE_URL=sqlite:///./data/adrobot-live.db
KEITARO_URL=https://your-tracker.example
KEITARO_API_KEY=ваш-существующий-ключ
```

Затем выполните миграции для выбранной базы и перезапустите приложение. `.env` и базы данных исключены из Git. Пароль от админки приложению не нужен; ключ используется только на сервере в заголовке `Api-Key`.

Адрес можно указать как корень трекера или как полный путь `https://your-tracker.example/admin_api/v1`. `/admin` добавлять не нужно. Приложение использует [официальный Keitaro Admin API](https://admin-api.docs.keitaro.io/). Версия и права конкретного экземпляра могут влиять на доступные операции; проверяйте их по документации в админке.

Нужны права чтения кампаний, потоков, офферов, доменов, групп и источников; для создания и публикации — права изменения кампаний и потоков. Автоматического создания или изменения API-ключей нет.

`DEFAULT_DOMAIN_ID`, `DEFAULT_GROUP_ID`, `DEFAULT_SOURCE_ID` необязательны. Их можно задать положительными числами. В форме также можно явно выбрать доступные домен, группу и источник. При отсутствии значения используется первый доступный элемент списка API.

В общем тестовом трекере используйте названия `test_фамилия_…`. Приложение не меняет кампании при открытии списка или обычном просмотре локальных данных. **Fetch Streams** только читает Keitaro и обновляет локальную базу. Внешние записи выполняются при создании кампании и публикации конкретного потока.

## Как проверить сценарий из видео

1. Выберите кампанию, нажмите **Fetch Streams**. Потоки без офферов отображаются без разбора их настроек.
2. Найдите оффер по названию или ID, выберите результат и нажмите **Добавить**. Поток станет черновиком, доли пересчитаются; Keitaro пока не изменится.
3. Закрепите долю кнопкой с булавкой. При необходимости измените процент. Остаток распределится между незакреплёнными активными офферами.
4. **Отменить** возвращает локальное состояние к последней загрузке или публикации. Новая неопубликованная привязка удаляется из локальной базы.
5. **В Keitaro** публикует офферы выбранного потока. После проверки ответа поток снова отмечается как синхронизированный.
6. **Удалить** переводит оффер в локальный архив с долей 0%. После публикации его привязка исчезает в Keitaro; локальная история остаётся. **Вернуть** восстанавливает его в черновике.
7. Если удалить оффер непосредственно в Keitaro и снова нажать **Fetch Streams**, известная привязка попадёт в локальный архив и останется доступной для восстановления.

В деморежиме внешний редактор можно имитировать через Swagger, метод `PUT /api/demo/streams/12/offers`. Например, тело `{"offers":[{"offer_id":101,"share":100,"state":"active"}]}` оставит во внешнем демопотоке только один оффер. После **Fetch Streams** остальные окажутся в локальном архиве. В режиме `live` этого маршрута нет.

## Правила и принятые решения

- Доли — целые проценты. Закреплённые доли сохраняются; оставшаяся часть делится поровну. Остаток от деления получают офферы с меньшим ID. Например, закреплённые 25% и два свободных оффера дают **25 / 38 / 37**.
- Закреплённые доли не могут превышать 100%. Если закреплены все активные офферы, сумма должна быть ровно 100%. Новый незакреплённый оффер при закреплённых 100% получает 0%.
- Удаление снимает закрепление. Восстановление включает оффер с незакреплённой долей. Отмена возвращает предыдущее состояние, включая закрепления.
- Пустой черновик допустим; публикация потока без активных офферов запрещена. Офферы со статусом `disabled`, полученные из Keitaro, сохраняют этот статус при публикации и не участвуют в распределении активного трафика.
- При загрузке внешние доли сохраняются как есть. Если их сумма отличается от 100%, используйте **Выровнять веса**. Загрузка сама по себе не меняет внешний трекер.
- Закрепления хранятся локально: у API Keitaro нет отдельного поля для закреплённой доли. Публикуются рассчитанные проценты.
- **Fetch Streams** сохраняет локальные черновики, если внешние офферы не изменились. При одновременных внешних изменениях возвращает `409`; отмените черновик и загрузите актуальную версию. Синхронизация кампании выполняется одной локальной транзакцией.
- Удалённый в Keitaro поток сохраняется локально с отметкой об удалении; редактирование блокируется. Его история не теряется.

## Публикация и ошибки

Перед публикацией сравниваются ID офферов, доли, статусы, схема и статус потока с последним снимком Keitaro. При конфликте возвращается `409`, локальный черновик сохраняется. Фильтры, лендинги, триггеры и прочие поля не отправляются в `PUT`: приложение обновляет только `offers`.

Каждая локальная правка передаёт `revision`. Устаревшая вкладка получает `409` и не затирает изменения другой вкладки. В SQLite записи сериализуются через `BEGIN IMMEDIATE`, для серверных SQL-баз предусмотрена блокировка строки потока через `SELECT FOR UPDATE`.

После публикации выполняется контрольное чтение Keitaro. При сетевой ошибке черновик остаётся. Если запрос успел выполниться, но ответ потерялся, повторная публикация распознаёт уже применённое желаемое состояние и завершает синхронизацию.

Новая кампания создаётся выключенной. После создания обоих потоков она включается. При ошибке создания потока приложение пытается перенести незавершённую кампанию в архив. Если компенсация тоже не удалась, сообщение содержит ID для ручной проверки. Автоматических повторов `POST` нет, чтобы не создавать дубликаты.

**Ограничение API:** между контрольным чтением и записью в Keitaro остаётся небольшое окно для внешней конкурентной правки. Admin API не предоставляет атомарного compare-and-swap; локальная транзакция не может устранить эту гонку на стороне другого сервиса. Также невозможно гарантировать откат внешней записи при падении процесса или локальной БД после успешного ответа Keitaro. Повторная публикация помогает согласовать такое состояние.

## Миграции

Основная схема создаётся только Alembic:

```bash
uv run alembic upgrade head
uv run alembic current
uv run alembic check
```

Приложение сообщает об отсутствии таблиц при запуске, вместо неявного создания схемы. Имитационный трекер использует собственную отдельную БД и создаёт только свою служебную таблицу автоматически. Для смены основной базы измените `DATABASE_URL` и выполните миграции заново. SQLite выбран для простого запуска; подключение PostgreSQL дополнительно требует установки SQLAlchemy-драйвера, например `psycopg[binary]`.

## Docker

```bash
cp .env.example .env
docker compose up --build -d
docker compose logs -f adrobot
```

Порт по умолчанию доступен только на `127.0.0.1:8000`. Миграции выполняются в entrypoint, данные сохраняются в именованном томе. Параметры подключения берутся из `.env`; сам файл не попадает в образ.

При внешнем развёртывании задайте `APP_USERNAME` и `APP_PASSWORD`, используйте HTTPS на обратном прокси. Без пароля приложение предназначено для локального запуска. Ключ Keitaro не передаётся браузеру и не возвращается в ошибках API. Внешние шрифты необязательны: при отсутствии интернета используются запасные шрифты, функциональность сохраняется.

## Проверки

```bash
uv run pytest -q
uv run ruff check .
uv run ruff format --check .
```

Тесты используют временные независимые базы и не обращаются к реальному трекеру. Проверяются сценарии создания, архивирования и восстановления, закреплённые веса, округление, отмена, внешние удаления, сохранение черновиков, конфликты, устаревшие ревизии, повтор после потерянного ответа, компенсация частичного создания, сохранность чужих полей и перезапуск приложения. Отдельно проверяются контракт HTTP-клиента и отсутствие ключа в ошибках.

## Структура проекта

```text
app/
  main.py           # API, зависимости, обработчики ошибок
  services.py       # черновики, синхронизация, создание и публикация
  gateway.py        # HTTP-клиент Keitaro и изолированный демотрекер
  models.py         # кампании, потоки, привязки офферов
  weights.py        # распределение целых процентов
  schemas.py        # валидация входных данных
  static/           # интерфейс без сборки
alembic/            # миграции основной базы
tests/              # поведенческие и контрактные тесты
```
